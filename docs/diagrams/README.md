# SignOff 架构与生态图

三张图，都用「方框 + 分区」而不是流程图：因为它们要回答的是**有哪些东西、它们之间是什么关系**，
不是“执行顺序”。源文件是纯 HTML/CSS，改文案后重新截图即可，不依赖绘图工具。

| 文件 | 回答的问题 |
| --- | --- |
| `signoff-1-capability.png` | SignOff 由哪些部分组成、判定发生在哪一层、什么东西会留在仓库里 |
| `signoff-2-market.png` | 已经出现在哪些社区与市场、哪些还在等审核、哪些物料备好但未提交 |
| `signoff-3-user.png` | 用户怎么装怎么用，以及平台差异、环境差异、已知坑的处置 |

对应的 HTML 源：`fig1-capability.html`、`fig2-market.html`、`fig3-user.html`。

## 图 1 的读法

从上到下是“谁在调用 → 谁在判定 → 判定结果落在哪 → 依赖什么”。要点：

- 四个入口（CLI、git 钩子、CI、MCP/技能）**共用同一个 `guard.js`**，所以结论不会互相矛盾；
- 五关是并列的，任何一关判红，整体退出码就是 1，**没有“部分通过”**；
- 提交信息里的 `Signoff-Pass: <tree>` 是审计的唯一线索，`--no-verify` 会让这条线索消失（审计里显示 `missing`）。

## 图 2 的读法

绿色=已经可被搜索/安装；黄色=已提交等待人工审核；灰色=物料已备好但没提交。
底部那行是关键：**registry 只是索引，不是流量**；真正带来访问的是人工清单与被引用。
