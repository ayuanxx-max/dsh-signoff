用户视角：安装、使用、以及可能踩到的东西

左边是正常路径，右边三块是“真实世界会不一样的三个维度”——平台、环境、已知坑
用户 / Agent
目标：装一次，之后不用记
失败模式：钩子没生效却以为生效了
① 安装 npm i -g dsh-signoff（或 npx dsh-signoff） · 硬要求只有 Node ≥18 与 git
全局装的是命令，项目里不产生依赖
公司网络下 npx 可能被代理挡
② 初始化 signoff init · 需要保留已有钩子时加 --chain
想让测试命令固定下来加 --lock-test
先看会写什么加 --dry-run
不想动 CI 加 --no-ci
③ 日常 git commit 自动跑五关 · 红了就按提示修，不绕过
不确定为什么加 signoff doctor
想知道某关规则用 signoff explain p2
想查“谁真的过了”用 signoff audit --since-install
④ 排错顺序（别跳步） doctor → doctor --fix → explain <gate> → 改配置 · 90% 的“没反应”是钩子被别的工具覆盖或没有执行位
改阈值是最后一招，改之前先问“这条断言是不是本来就该有”
⑤ 退出 / 边界 signoff uninstall 三档（默认 / --keep-config / --all） · 它不测“代码好不好”，只判“这次完成是否可证明”
锁是单机单仓库尽力而为，不是分布式锁

平台差异

平台会不一样的地方
Windows钩子用 .ps1/.cmd 启动器；执行位不生效；控制台默认 GBK，中文输出可能显示乱码（内容本身没坏）
macOS / Linux钩子必须有执行位（init 会设，doctor --fix 能补）；/bin/sh 语义差异
容器 / CI常没有 user.name/user.email，提交会失败，与闸门无关
SMB / NFS锁的原子性无法被证明；mkdir 比 O_EXCL 可靠，但仍属尽力而为

环境差异

环境症状
Node 版本18/20/22/26 都在 CI 里测过；更老的 Node 不支持
浅克隆审计需要基线提交可达；CI 必须 fetch-depth: 0，本地 --depth 1 会判红
monorepo在子目录跑时，配置与状态目录按“仓库根”识别；子包各自 init 会造成两套钩子，用 doctor 看出重复
无测试的仓库P1 会退化到后备命令；命中不了就如实报“未识别到测试命令”，不假装通过
代理 / 离线除 npx 取包外不联网；闸门本身离线可用

可能的坑（现象 → 处置）

现象处置
commit 没跑闸门钩子被 husky 等覆盖 → init --chain；doctor 会指名是谁占了钩子
P1 卡住 / 选错命令init --lock-test 固定本机识别结果；或 --test-cmd
audit 报 not an ancestorrebase/强推/换克隆 → init --reset-install；想审计别的时间窗用 --range A..B
锁等待超时调 SIGNOFF_LOCK_WAIT_MS；确认无进程后删 .signoff/lock/
P2 过严 / 过松改 config.json 阈值；--strict 是给“有场景无断言”用的
P5 误报占位符只在词边界命中；中文复合词不会误伤。真误报就改写措辞，别改词表
CI 里 P4 判红workflow 缺 fetch-depth: 0，基线提交不可达
